# Platform split: `android` and `ios`

One Dart codebase serves both platforms, told apart at runtime from `Platform.isIOS`, with no build flavors. The split exists so that iOS work means writing Swift behind a seam that is already there, not untangling Android from shared code. Mechanics: `../features/app-foundation.md`.

- **No `--flavor`.** On iOS a flavor means Xcode schemes and per-flavor configurations inside `project.pbxproj`, a file that must be edited with care (`../features/app-foundation.md`, Gotchas). With `foss` gone, Android has no flavor axis either. Code names the axis `AppPlatform`, because platform is what it truthfully is.
- **`foss` (F-Droid) dropped.** Firebase is a native dependency of the Android app, and `mobile_scanner` ships ML Kit, a proprietary blob F-Droid rejects outright. A `foss` flavor would carry permanent build complexity for a channel Zuno is not pursuing. Reopening it means solving both the FCM split and a scanner swap, and a replacement scanner must hand over the verification QR payload as raw bytes (`../features/security-verification.md`).
- **A pure, table-tested function, not a service.** `capabilitiesFor(AppPlatform)` returns a const `PlatformCapabilities`, exposed as the overridable `platformCapabilitiesProvider`, the same idiom as `accountSecurityStatus`.
- **A capability flag with a safe no-op by default, and an interface only where iOS reimplements** (the call seams). An interface with one real implementation and a no-op is a flag with extra ceremony.
- **Call sites never read `Platform.isIOS`.** They take capabilities, so the iOS path runs under `flutter test` on any host.
- **Every field is required**, so a new flag is decided for both platforms when it is added. An iOS `false` means "no handler yet", except for Android concepts and the Android seam selectors, which stay `false` for good: CallKit is a new branch in each call factory, never a flip of an Android selector.
- **Every `zuno/*` channel is gated**, because an ungated call throws `MissingPluginException` on the platform without a handler.
- **The call seams separate presentation from routing.** How a ring is presented differs per platform, but cross-isolate decline and action routing is platform-neutral and the subtlest code in the app, so it stays in one place, `call_notification_service.dart`. A seam method that seems to need that routing is drawn wrong.
- **Delivery modes are per platform** (`../features/notifications.md`). A stored mode this platform lacks falls back to its default rather than selecting a dead transport. Stopping the unselected modes still loops over every mode, the cheapest guarantee that two transports never run at once.
- **Android-only plugins** (`unifiedpush`, `zuno_vibration`, `zuno_call_style`, `zuno_notifications`) declare only `android` in their pubspecs, and every call into them is gated.
