# Platform split: `android` and `ios`

One Dart codebase serves both platforms, told apart at runtime from `Platform.isIOS`; neither platform has build flavors. The split exists so that iOS work means writing Swift behind a seam that is already there, not untangling Android from shared code. Mechanics: `../features/app-foundation.md`.

- **No `--flavor`.** On iOS a flavor means Xcode schemes plus per-flavor build configurations inside `project.pbxproj`, a file that must be edited with care (`../features/app-foundation.md`, Gotchas). With `foss` gone, Android has no flavor axis either, so neither platform passes `--flavor`. Code names the axis `AppPlatform`, because without a build-time flavor, platform is what it truthfully is.
- **`foss` (F-Droid) dropped.** Firebase is a native dependency of the Android app (`firebase-messaging` through the BoM, used by `FcmService` and the FCM router), so a Firebase-free APK would need a flavor that drops that dependency and those classes. `mobile_scanner` also ships ML Kit, a proprietary blob F-Droid rejects outright. A `foss` flavor would carry permanent build complexity for a channel Zuno is not pursuing. Reopening F-Droid is a fresh decision that must solve both the FCM split and a scanner swap. A replacement scanner must hand over the verification QR payload as raw bytes: a String-shaped scanner API corrupts it silently, and only an on-device scan proves a replacement handles it (`../features/security-verification.md`).
- **A pure, table-tested function, not a service.** `capabilitiesFor(AppPlatform)` returns a const `PlatformCapabilities`, exposed as the overridable `platformCapabilitiesProvider`. It is the same idiom as `accountSecurityStatus`.
- **A capability flag with a safe no-op by default; an interface only where iOS reimplements** (the call seams). An interface with one real implementation and a no-op is a flag with extra ceremony.
- **Call sites never read `Platform.isIOS`.** They take capabilities, so the iOS path runs under `flutter test` on any host.
- **Every field is required**, so a new flag is decided for both platforms when it is added. An iOS `false` means "no handler yet", except for Android concepts and the Android seam selectors, which stay `false` for good: CallKit is a new branch in each call factory, never a flip of an Android selector.
- **Every `zuno/*` channel is gated.** Ungated, a call throws `MissingPluginException` on the platform without a handler and lands in the global error handler. The channel table is in `../features/app-foundation.md`.
- **The call seams separate presentation from routing.** How a ring is presented differs per platform: a full-screen CallStyle notification on Android, a CallKit report on iOS. Cross-isolate decline and message-action routing (the `IsolateNameServer` ports in `live_isolate_route.dart` and the headless response handler) is platform-neutral and the subtlest code in the app, so it stays in one place, `call_notification_service.dart`. A seam method that seems to need the port machinery is drawn wrong.
- **Delivery modes are per platform** (`deliveryModes`; the modes and their settings are in `../features/notifications.md`). A stored mode this platform lacks falls back to its default; otherwise a carried-over preference would select a dead transport and silently deliver nothing. Stopping the unselected modes still loops over every mode, not just this platform's: the cheapest guarantee that two transports never run at once.
- **Android-only plugins** (`unifiedpush` and the local `zuno_vibration`, `zuno_call_style` and `zuno_notifications`) declare only `android` in their pubspecs, and every call into them is gated.
